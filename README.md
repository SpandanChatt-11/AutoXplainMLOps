# AutoXplain — MLOps Edition

Refactored from the original notebook-based project into a proper engineering pipeline: separated
data/feature/train/inference stages, MLflow experiment tracking and model registry, conformal
prediction intervals (MAPIE), a pytest suite, Docker packaging, and CI via GitHub Actions.

**The ML itself is unchanged** — same data, same four models (Ridge, Random Forest, XGBoost, SVR),
same log-transform, same SHAP/LIME explainability. This pass is about the engineering *around* the
model, not the model.

## What's new vs. the notebook version

| Before | Now |
|---|---|
| One-off notebook runs | `src/data_prep.py`, `src/features.py`, `src/train.py`, `src/inference.py` — separated, testable stages |
| Manually pick the best model | MLflow tracks every run; best model auto-registered to a Model Registry `production` alias |
| Flask app loads a local pickle | Flask app loads the **registered** model (local pickle only as a fallback) |
| Single price prediction | Point estimate **+ a MAPIE-calibrated 90% prediction interval** |
| No automated tests | 31 pytest tests — parsing logic, encoding correctness, real inference, real Flask routes |
| Manual deployment | Dockerized; GitHub Actions runs tests + builds the image on every push |

## Running Locally — Step by Step

**1. Set up the environment**
```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

**2. Place your raw scraped data**
Copy your scraped CSV to `data/raw/cardekho_kolkata_scraped_data.csv` (or pass a custom path in the next step).

**3. Build the ML-ready dataset**
```bash
python -m src.build_dataset data/raw/cardekho_kolkata_scraped_data.csv data/processed/cardekho_kolkata_ml_ready.csv 
```
This cleans, feature-engineers, geocodes (real Nominatim calls — this step takes a few minutes and needs network access), and one-hot encodes the data. It also saves `models/category_metadata.pkl`, which downstream steps depend on.

**4. Train, tune, and register the models**
```bash
python -m src.train data/processed/cardekho_kolkata_ml_ready.csv
```
This trains and tunes all 4 models with 5-fold CV, logs everything to MLflow (`mlflow.db` + `mlruns/` are created here), registers the best model with a `production` alias, calibrates MAPIE on a held-out split, and saves local fallback artifacts to `models/`. **This takes a while** (full hyperparameter search across 4 models) — expect somewhere in the 10-20 minute range depending on your machine.

**5. Inspect experiments in the MLflow UI (optional but recommended)**
```bash
mlflow ui --backend-store-uri sqlite:///mlflow.db
```
Open `http://127.0.0.1:5000` (MLflow's own UI, not the Flask app) to see every run's parameters, metrics, and the registered model.

> **Windows note**: MLflow's UI defaults to 4 worker processes, and on some Windows setups one or more of them fail to bind with `OSError: [WinError 10022]`. In testing, this looked alarming but was harmless — one worker failed while the others served the UI normally. If you'd rather avoid the noisy traceback entirely, run with a single worker instead: `mlflow ui --backend-store-uri sqlite:///mlflow.db --workers 1`.

**6. Run the tests**
```bash
pytest tests/ -v
```
Should show 31 passed. If `test_inference.py` or `test_app.py` fail, it usually means step 4 hasn't been run yet — those tests load real artifacts from `models/` and the MLflow registry.

**7. Run the Flask app**
```bash
python app/app.py              # Windows-friendly, dev server
# or, Mac/Linux:
gunicorn app.app:app --bind 127.0.0.1:5000
```
Open `http://127.0.0.1:5000`.

**8. Build and run the Docker image** (requires Docker installed; steps 3-4 must have already run so `models/`, `mlflow.db`, `mlruns/` exist)
```bash
docker build -t autoxplain .
docker run -p 5000:5000 autoxplain
```

## CI (GitHub Actions)

On every push/PR to `main`: installs dependencies, runs the full pytest suite, and (if tests pass) builds the Docker image to confirm it builds cleanly. No deployment step — this validates correctness, it doesn't push anywhere.

## A deliberate simplification, stated plainly

`models/`, `mlflow.db`, and `mlruns/` are committed to git (not the usual practice for model binaries) so that CI can run real, non-mocked tests and build a working Docker image without needing a live external model store. A production system would use a proper artifact store (S3, a hosted MLflow tracking server, or DVC) instead. Worth being upfront about this trade-off if it comes up in an interview — it's a reasonable call for a portfolio-scale project, not the right call at production scale.
